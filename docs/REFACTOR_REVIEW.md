# 数据包架构审查与重构建议

- 日期：2026-10-28
- 目标：Minecraft Java 1.21.11
- 范围：当前工作区全库静态审查；不是提交差异审查，也不是 v0.3 实现验收。
- 结论：**需要重构，优先收束生命周期、状态清理和计时器；保留可用的技能、枪械、地图与生成模型，按模块逐步迁移。**

> 本报告保留重构前的静态证据。随后已实施生命周期、清理、个人计时、结果与设备归属重构，当前实现和验证范围见 [ARCHITECTURE.md](ARCHITECTURE.md)。

## 1. 判断依据

已经出现可由源码追踪的跨局属性残留、延迟回调污染新局和模式混用风险，重构的收益来自减少真实错误与修改点，不只是整理目录。

当前规模（排除空行和独立注释统计命令行）：

| 项目 | 实际扫描结果 |
|---|---:|
| `escape_island` 函数 | 445 |
| `skill` 函数 | 389 |
| 手写函数合计 | 834 |
| 手写函数总行数 | 9,754 |
| 手写命令行数 | 8,802 |
| `animated_java` 生成函数（单独统计） | 160 |
| `test/` 函数 | 71 |
| 正式开局 / 测试开局命令行 | 244 / 240 |
| 两个开局函数顺序匹配的命令行 | 232 |

232 行匹配约占正式开局 95.1%、测试开局 96.7%；这是去掉空行/注释后的顺序匹配结果，不是整库重复率。数据包的小函数、射线递归、道具显示函数和生成动画本身不构成重构理由。

现有目录已经区分 `game`、`infection`、`task`、`escape`、`skill`，仍有复用价值。真正欠缺的是：谁拥有状态、如何进入/退出状态、退出时必须撤销哪些副作用。

## 2. 按优先级排列的发现

P1 表示可能破坏对局结果、跨局公平性或既定技能行为；P2 表示显著增加维护和回归风险。以下均来自静态调用链；尚未在游戏中复现。

### F1 · P1 · 上一局的延迟结算可以结束新一局

**证据**：

- `data/escape_island/function/game/end_all_infected.mcfunction:1`：锁定结局并将 `in_game` 设为 0，随后第 10 行预约 60 tick 后执行 `end_all_infected_finish`。
- `game/end_all_infected_finish.mcfunction:1`：无对局身份检查，直接解除 `ending_triggered`，再执行 `end_mutate`。
- `game/end_mutate.mcfunction:1`：只有结局锁检查，随后关闭对局并调用 `settle`。
- `game/start.mcfunction:21`、`:29`：新局将 `in_game` 设为 1、结局锁设为 0；没有取消上述预约。
- 正式 `start`、`abort`、`settle` 均未统一取消这些对局预约；测试清理反而在 `test/end_game_clear.mcfunction` 内维护了额外的 `schedule clear` 列表。

**可复现路径**：触发全员感染 → 在三秒演出内开始新一局 → 旧 `end_all_infected_finish` 到期，重置新局的结局锁并结束新局。旧末期 `end_mutate` 预约也有同类退出后遗留风险。

**建议**：对局生命周期统一拥有开始、结束与中止；新局有递增的对局 ID。核心结算时限优先由该局的截止时间推进，避免无归属的预约回调。保留的预约必须有完整注册/取消及归属校验。结束入口只能提交结果，由同一出口锁定一次并清理。

### F2 · P1 · 母体属性没有在正式结算/开局时恢复

**证据**：

- `data/escape_island/function/game/_make_mother.mcfunction:48`：母体设置基础护甲 4、护甲韧性 2、抗击退 0.8。
- `game/settle.mcfunction:7`：仅恢复移速、生命、攻击力与攻速，没有恢复上述三项。
- `game/start.mcfunction:244`：属性恢复仅处理移速，幸存者基础装备函数也没有补齐。
- `dev/_reset_player_state.mcfunction:125`：开发清理明确把护甲、韧性与抗击退归零，表明正式流程与开发流程已经分叉。

**影响**：上一局仍存活的母体结算后成为下一局幸存者，可以保留母体防御属性，造成难以从装备观察到的优势。不能依赖死亡、手动 reset 或恰好再次当母体来修复。

**建议**：建立一个玩家临时状态清理入口，集中恢复本包修改过的属性、临时标记、技能计时、实体和物品。正常结算、中止、训练退出、正式开局都复用它；长期生涯数据不属于该入口。对每个模块明确“进入时设置什么、退出时撤销什么”。

### F3 · P1 · 治愈的个人抗性计时丢失执行玩家

**证据**：

- `data/escape_island/function/infection/cure.mcfunction:12`：给当前玩家添加 `state.infection_resist`。
- 第 13 行使用 `schedule function escape_island:infection/_remove_resist 400t`。
- `infection/_remove_resist.mcfunction:1`：仅执行 `tag @s remove state.infection_resist`。
- `infection/add_spore_load.mcfunction:4`：后续污染计算继续读取该标记。

Java 的定时函数重新取得游戏循环执行源，不保留调用者这个玩家；回调中没有重新选择实体。因此正常到期路径不能移除原玩家的标记，20 秒减污染效果可能一直保留到其他清理入口执行。多人共用同一个预约函数，也不能表达各自独立的到期时间。

**核对方式**：读取当前版本 JSON 中的 Mojang 官方 `client_mappings`，用本机 `javap` 检查该版本原版 jar 的 `FunctionCallback`（映射名 `fsv`）；其回调从 `ServerFunctionManager.getGameLoopSender()` 取执行源，而非保存玩家执行源。此为字节码核对，未启动游戏。[官方版本映射](https://piston-data.mojang.com/v1/objects/031a68bebf55d824f66d6573d8c752f0e1bf232a/client.txt)

**建议**：个人效果使用个人剩余时间或到期时刻，由感染模块按目标玩家更新。检查 `skill:mother/_disguise_expire` 等同样直接依赖 `@s` 的预约回调，按相同原则修复。不要把玩家 `@s` 隐含保留作为定时函数的前提。

### F4 · P1 · 中止和重载没有可靠的退出语义

**证据**：

- `data/escape_island/function/game/abort.mcfunction:4`：关闭 `in_game`，清理部分 UI、效果和吞噬状态；保留多数阵营、职业、感染/死亡标记、角色分数及其他任务运行状态。
- `tick.mcfunction:46`：只要没有正式对局且存在感染期、死亡、孢化或 `role=1..` 玩家，就启用 `training/tick`，不要求明确进入训练。
- `training/_tick_20.mcfunction:6`：继续感染、转化、复活与职业 tick。
- `load.mcfunction:259`：每次加载直接把 `in_game` 设为 0，却没有按中止流程清理现有对局。

**影响**：中止后仍可能继续感染、转化、母体技能与职业更新；正式局 `/reload` 后可能被根调度误认为需要训练更新。即使正常结算移除了角色 tag，`role` 分数仍未统一归零，会继续满足训练兜底条件。重载、中止、正常结束目前具有不同且不完整的后置状态。

**建议**：明确空闲、正式对局、训练和独立小游戏的运行模式；训练应显式进入，不靠残留字段推断。短期选择“重载安全中止”即可，无须先做复杂的无缝恢复；注册函数与运行状态恢复/终止分开。调度与技能入口检查明确模式和有效玩家资格。

### F5 · P2 · 正式与测试初始化复制，已经发生行为漂移

**证据**：

- `data/escape_island/function/game/start.mcfunction` 与 `game/start_test.mcfunction` 分别有 244、240 条命令，其中 232 条顺序匹配。
- 正式入口重置 `p2_ambient_cd`、伪造信号与部分通讯员状态，测试入口缺少对应步骤。
- 测试入口第 87 行移除旧 `role.mechanic`，正式入口的角色清理段遗漏该 tag（反而重复移除 `role.marine`）。
- `role/_tag_doctor.mcfunction` 等只添加新职业，`role/give_kit.mcfunction` 则按所有残留职业 tag 分别发装备。由训练/开发机修工直接开正式局时，旧 tag 可能与新职业共存。

**影响**：测试通过不能充分代表正式开局；新增字段时必须在多份初始化/清理清单同步修改。角色 ID、职业 tag、原版 team、感染 tag 也可能彼此不一致。

**建议**：正式/测试入口仅处理人数校验、测试配置和附加物品，随后调用同一个初始化流程。职业切换通过一个入口清理旧职业、设置新职业并发装备；列出并检查“当前职业唯一”等不变量。测试构造只覆盖必要字段，复用真实转移函数。

### F6 · P2 · 对局结束条件分散，正确性依赖调用顺序

**证据**：

- `data/escape_island/function/game/_tick_20.mcfunction:52`：先判母体死亡后的清剿，再判无人类，随后继续处理撤离 tick。
- `infection/turn.mcfunction:87`：转化函数内部也能立即触发全感染结局。
- `escape/_ending_resolve.mcfunction`：另有撤离人数、自爆等待和路线分发。
- 各 `game/end_*` 同时修改结局锁、运行状态与 UI；`end_all_infected_finish` 还会重开结局锁。

已有 `ending_triggered` 锁和 `_ending_resolve` 是可保留的基础，不能说完全没有仲裁；问题是它们没有覆盖统一的状态快照、优先级与所有入口。

**影响**：同时死亡/转化/起飞、母体死亡时仍有待孢化者、动画结束时才触发撤离等情形，修改某一模块时必须理解多个入口的执行顺序。v0.3 的时间边界和部分撤离会继续放大这种成本。

**建议**：感染模块只报告新的玩家状态，撤离模块报告撤离资格和人数；对局模块在确定的更新点统一决定结果，再交给表现与清理流程。保留现有具体结局的文案/音效函数，但不让其各自拥有不同的结算协议。

### F7 · P2 · 测试工具有用，但不足以支撑大规模安全重构

**证据**：

- `data/escape_island/function/test/full_simulation.mcfunction:1`：仅设置 debug 并声称“计时器加速 x5”；实际 `game/phase_check` 仍按每次加 1 推进，未找到读取 debug 后加速的实现。
- `test/perf_check.mcfunction:1`：仅提示人工运行 `/perf start`，没有文档所述的模拟、迭代与耗时汇总。
- `test/spawn_dummies` 生成 mannequin，正式主线大量使用 `@a`；人偶不能替代真人验证人数、职业分配和完整对局状态机。
- `docs/TEST_PLAN.md` 列出 `test/regression_M2`，当前没有对应函数文件。
- 现有部分测试确实有条件检查与结果提示，但大量入口用于配置场景或让人目测，不能视为已经具备完整自动化回归。

**建议**：保留手测菜单；先补少量能判定结果的生命周期回归：连续两局属性一致、中止后不再推进、旧回调不影响新局、两人治疗独立到期、训练切正式局无职业残留。不要把所有函数都补成逐行镜像测试。性能另用真实服务器 profile，不能把静态扫描当作 TPS 结论。

## 3. 建议的模块职责

无需先搬动全部文件。可以在现有 namespace 下建立稳定入口，逐个把旧调用转到这些入口；表内是职责建议，不代表现有函数已经具备这些保证。

| 模块 | 负责的状态与行为 | 对外约定 |
|---|---|---|
| 对局生命周期 | 模式、对局 ID、时钟、阶段、结束申请、结果锁、退出协调 | 开局、中止、推进、提交结局；一次结束只生效一次 |
| 玩家状态 | 阵营、生命阶段、职业、形态、基础属性恢复 | 通过明确的状态转移修改；临时状态可完整清理 |
| 感染 | 污染、感染期、个人抗性、孢化、复活资格 | 更新自身状态，报告转化/死亡；不直接决定整局结局 |
| 任务与撤离 | 设备进度、任务物品、呼叫、候机、起飞资格 | 报告目标达成/撤离快照；不自行重置玩家或重开结局锁 |
| 技能与表现 | 职业能力、枪械、临时实体、UI、模型 | 暴露启用、更新、停用/清理入口；只在合法模式与状态执行 |

玩家状态应按独立维度建模：阵营、生命阶段、职业、母体形态各自有唯一合法取值，不把它们强行塞进一个大枚举。原版 team 作为友伤/可见性输出，避免和逻辑阵营分别被各模块随意改写。Scoreboard 与 tag 仍可继续使用，重点是明确写入者与不变量。

不建议为了“架构好看”先引入全局事件总线、统一任意任务框架、全面宏化或新的构建语言。先解决已经出现的变化点和重复，保留简单的函数调用。

## 4. 迁移顺序与退出条件

### 第一批：修复阻断性生命周期问题

1. 统一结束与中止清理，恢复本包改动过的属性；禁止旧回调影响后续对局。
2. 把个人抗性等计时改成按玩家独立更新。
3. 明确重载行为，并移除“靠残留职业分数推断训练模式”的启动方式。

退出条件：连续两局、治疗到期、中止后等待、结局演出内重开、正式局重载均有可判定的结果。

### 第二批：抽取共用初始化与玩家状态入口

1. 正式和测试开局复用同一核心；清理职责按玩家/世界/模块拆分，避免只把 250 行换个文件继续复制。
2. 训练、开发工具、职业切换复用这些入口，明确需要保留的训练配置。
3. 整理状态登记表：字段、所有者、作用域、初始化值、退出处理；把最重要的不变量加入测试。

退出条件：添加一个临时技能字段不再需要分别修改多份全局清理清单；正式与测试只保留有意的配置差异。

### 第三批：统一结算，再接入 v0.3 主线

1. 集中判断清剿、全感染、撤离和超时；用针对边界场景的回归固定现行行为。
2. v0.3 三选二协议接到已有生命周期和结果模块；版本差异限制在任务规则、时限与判定策略。
3. 保留枪械命中、技能细节、直升机模型/地图资产；逐项调整需要变化的入口。

退出条件：v0.3 任务完成不会绕过最终通讯直接呼叫飞机；旧 15 分钟规则不会误触发；跨局清理和结果只执行一次。

`mother_respawn` 这类看似旧逻辑的函数可以列入后续清理候选，但仅凭没有静态调用就删除并不充分：管理员命令、菜单、宏或外部数据包可能使用它。先确认入口再移除，不先批量改名或删文件。

## 5. 本次验证与边界

- 解析了 99 个 JSON/元信息文件，未发现 JSON 语法错误；不等于完成 Minecraft 命令/组件语法验证。
- 扫描了函数调用与标签/advancement 奖励入口。手写函数的字面函数引用已能在本包及同级依赖中解析；`motion:apply_scoreboard` 实际存在于同级 `FastMotion`，不算缺失。
- Animated Java 中的动态宏路径不能按截断的字面字符串判作缺失；生成代码不计入手写重复结论。
- 核对了主要调度、开局/结算/中止、训练、感染/死亡、撤离、个人定时效果和测试入口。未声称逐条验证全部 8,802 条命令。
- 对 `schedule` 的执行上下文补充了本地 1.21.11 原版 jar 与 Mojang 官方映射核对；没有启动游戏、运行世界或改动存档。
- 未运行多人对局、服务器 profile 或 Minecraft 命令解析器，因此不判断真实 TPS、射线性能或最终平衡。
- 本次只新增审查报告；没有开始代码重构，也没有改动上一轮的玩法设计稿。
